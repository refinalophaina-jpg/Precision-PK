### New findings raised during the fix

- **N1 — the in-app AUC uncertainty was overstated.** It claimed `~±15%` at one level; simulation
  against the verified Buelga prior (n=2000) puts only **66%** of patients inside ±15%
  (median 10.3%, p80 20.9%, p90 28.3%). Now quoted at the ~80th percentile with the
  percentile stated, and the 2-compartment figures explicitly marked *estimated, not simulated*.
- **N2 / N3 — RESOLVED.** The first implementation used targets of 21.5 / 22.0 taken from the
  original prompt, which broke the seam: IBW stepped 9.7% for women at 152.4 cm and became
  **non-monotonic** (a 152.3 cm woman got a higher IBW than one at 152.5 cm). Flagging it
  found the cause. GlobalRPH does not choose round targets — it **derives** them from the
  Devine anchor (`50 / 1.524²` = 21.53 male, `45.5 / 1.524²` = 19.59 female; refs Wiggins
  2004, ADA Renal Care p.12; Barash 1989 ch.47:1231), which makes the join continuous by
  construction. Now implemented that way and verified: 152.4 cm returns exactly 45.50 / 50.00,
  and GlobalRPH's own test case (55 in male → 42.0 kg) reproduces at 42.01. The 21.5/22.0
  figures belong to a different method (Tokunaga 1991) and must not be grafted onto the
  Devine anchor. GlobalRPH's underweight rule — actual body weight wins when it is below the
  selected basis — is also now applied in `pickCrClWeight`.
- **N4 — regimen detection read the wrong regimen.** `inferCurrentRegimen` used the modal
  interval across the whole history, so a deliberate q12h→q8h change was reported as an
  accidental early dose and projections used the abandoned regimen. Replaced with
  recency-based `detectRegimen`; see `phase4_regimen_validation.cjs`.

## Findings

### A1 — Goti SCr truncation uses age > 65; the paper says age > 60 · **HIGH**

`index.html:5110` — `if (scr < 1.0 && age > 65) scr = 1.0;`

Goti 2018, Methods (p. 471 of the accepted manuscript):

> "Serum creatinine (Scr) values were truncated to 1 mg/dl if the Scr value was <1 mg/dl
> and the patient's age was **>60 y** and then these truncated SCr values were used in the
> CrCL calculation."

Patients aged **61–65 with SCr < 1.0** therefore get no truncation in the app, while the
model was *estimated* with truncation applied to them. Their CrCl is overstated, and since
`TVCL = 4.5 · (CrCl/120)^0.8`, so is their prior clearance — and dose scales with clearance.

Reproduced (`goti_age.cjs`):

| Patient | CrCl (code) | CrCl (paper) | TVCL code | TVCL paper | Prior CL inflated by |
|---|---|---|---|---|---|
| 62 M, 80 kg, SCr 0.7 | 123.8 | 86.7 | 4.61 | 3.47 | **+33.0%** |
| 61 F, 65 kg, SCr 0.6 | 101.0 | 60.6 | 3.92 | 2.61 | **+50.5%** |
| 63 F, 70 kg, SCr 0.5 | 127.3 | 63.6 | 4.72 | 2.71 | **+74.1%** |
| 64 M, 80 kg, SCr 0.9 | 93.8 | 84.4 | 3.70 | 3.40 | +8.8% |

**Caveat, stated honestly:** this is the *prior*. With observed levels the MAP fit pulls
toward the data, so the clinical impact is greatest for empiric dosing and for patients with
one level, and shrinks as levels accumulate. It is still a wrong prior for a well-defined
band of patients.

The code comments the rule as an "erratum SCr floor". If a published erratum genuinely moved
60 → 65, that citation must be recorded in the code; the primary text does not support 65.
**Resolve the citation before changing the number.**

**Fix:** `age > 60`, with the source line quoted in a comment — or, if the erratum says
otherwise, cite it.

### A2 — "Buelga" names two different models in the same application · **HIGH**

Module 1's `buelga` (`:2947`, `:2957`) is `CL = 1.08·CrCl·0.06`, `Vd = 0.98·TBW`.
Module 2's Buelga prior (`:5058`) is `CL = 4.47·(CrCl/100.8)^0.85·(TBW/76)^0.13`,
`V = 58.9·(TBW/76)^0.65`. These are not the same model, and they do not agree:

| CrCl | Module 1 CL | Prior CL | Ratio |
|---|---|---|---|
| 20 | 1.296 | 1.130 | ×1.15 |
| 60 | 3.888 | 2.876 | ×1.35 |
| 80 | 5.184 | 3.673 | **×1.41** |
| 120 | 7.776 | 5.184 | ×1.50 |
| 150 | 9.720 | 6.267 | **×1.55** |

A clinician selecting "Buelga" in the trough module and "Buelga" in the AUC module gets
clearances differing by 15–55%, rising with renal function. The app's own model-info text
(`:3219`) says *"Buelga (2005) — population PK model used as Bayesian prior in DoseMeRx.
Tends to overestimate CL"* — which describes the Module-1 form's behaviour relative to the
actual Buelga prior, suggesting the Module-1 entry is mislabelled rather than the prior.

**Fix:** establish which (if either) is Buelga 2005 — see [Not yet verified](#not-yet-verified)
— then rename the other. Two models may legitimately coexist; two models under one name may not.

### A3 — Blank inputs become legal-looking zeros in Module 1 · **HIGH**

`:2920` — `function v(id) { return parseFloat(document.getElementById(id).value) || 0; }`,
used at 72 call sites. A blank or non-numeric field reads as **0**, and 0 is a plausible
value for age, weight, SCr, dose and interval. Reproduced:

| Blank field | Result |
|---|---|
| SCr | `calcCrCl(60,'M',0,80)` → **Infinity** (divide by zero) |
| weight | `Vd = 0 L`, `CL = 0 L/h` → peak **Infinity** |
| age | `calcCrCl(0,'M',1,80)` → **155.56** mL/min — arithmetically valid, clinically meaningless |

These propagate into `innerHTML` result cards and render as text rather than raising.

**The same app already knows better.** `getBayesCrCl` (`:4786`) guards properly:
`if (!age || !scr || !tbw) return null;`. Module 1 and Module 2 disagree about whether a
blank field is an error.

**Fix:** a single `num(id, {min, max, required})` helper returning `null` on invalid, with
Module 1's call sites migrated to it. This is the precondition for A4.

### A4 — No upper-bound validation anywhere · **MEDIUM**

No field has a plausibility ceiling. Reproduced:

| Input | Result |
|---|---|
| age 200 | CrCl **−66.67** mL/min — a negative clearance, accepted |
| weight 500 kg | CrCl 625.00 |
| height 300 cm | IBW 183.65 kg |
| dose 50,000 mg | accepted |

Validation is 18 scattered `alert()` calls (`:3237`–`:6054`) and is uneven: the two-level

### A5 — `calcPeakTrough`'s numerical guard reports the opposite of the truth · **MEDIUM**

`:2969` — `if (eKelTau >= 0.9999) return { peak: dose/vd, trough: 0 };`

The guard fires when `kel·tau ≤ 1e-4`, i.e. effectively **no elimination between doses**. In
that regime the trough should approach the peak (unbounded accumulation). Returning
`trough: 0` states the reverse, and a zero trough reads as "room to increase the dose".

Reproduced: with `kel = 0, tau = 24, dose = 1000, Vd = 70` → peak 14.29, **trough 0.00**.
Downstream that yields AUC24 174.93 — a low-looking exposure that would prompt escalation in
a patient who is in fact eliminating nothing.

**Reachability is conditional on A3/A4**: `kel = 0` needs `CL = 0`, which needs `CrCl = 0`,
which needs age = 140 (accepted, per A4) or a blank weight (accepted, per A3) — and only for
the `buelga`/`matzke`/`bauer` clearance forms, since `vancopk` has a `+4` intercept that
never reaches zero. So it is a second line of defence that is also wrong, rather than an
independently reachable bug. Fixing A3 and A4 largely closes it; the guard should still
return an error rather than a number.

### A6 — Matzke Vd steps discontinuously at CrCl 60 · **MEDIUM-LOW**

`:2959` — `(crcl > 60 ? 0.72 : 0.89) * tbw`. Reproduced at 1000 mg q12h, 80 kg:

| CrCl | Vd | Peak | Trough | AUC24 |
|---|---|---|---|---|
| 60.0000 | 71.20 L | 37.70 | 24.84 | 740.7 |
| 60.0001 | 57.60 L | 39.42 | 23.54 | 740.7 |

A 0.0001 mL/min change in CrCl moves Vd by **−19%**, the peak by +4.6% and the trough by
−5.2%. **AUC24 is unaffected** (it depends on CL, which is continuous), so in an AUC-primary
tool the blast radius is limited to the displayed peak/trough and any trough-based guard that
straddles the boundary. Worth a note in the UI rather than a silent cliff.

### A7 — Module 1 and Module 2 use different SCr floor policies · **MEDIUM**

| | Module 1 `calcCrCl` (`:2936`) | Module 2 `getBayesCrCl` (`:4791`) | Goti `getGotiCrCl` (`:5110`) |
|---|---|---|---|
| SCr floor | 0.8, **only if age ≥ 65** | max(SCr, 0.7 M / 0.6 F), **always** | 1.0 if SCr<1 **and age>65** (see A1) |
| Clamp | none | [5, 150] | [5, 150] |

Three different rules for the same quantity. The Goti-specific one is defensible (it
reproduces that model's estimation conditions); the Module 1 vs Module 2 divergence is not
obviously intentional. The same patient's CrCl differs between tabs.

I initially suspected the divergence was much larger, because Module 1 appeared to use raw
TBW. It does not — `updateCrCl` (`:3204`–`:3207`) applies the same AdjBW-if-TBW>1.2×IBW rule
as Module 2, consistently across all four call sites (`:3208`, `:3254`, `:3307`, `:3353`).
The residual divergence is the floor policy and the clamp only.

### A8 — Selecting "AdjBW" yields IBW for non-obese patients · **LOW**

`:3205`–`:3207` — `const adjbw = tbw > ibw*1.2 ? calcAdjBW(tbw, ibw) : ibw;` then
`case 'AdjBW': wt = adjbw;`. If TBW ≤ 1.2×IBW, choosing "AdjBW" silently supplies **IBW**,
not adjusted body weight (which would be ~1.08×IBW at the boundary — about 8% higher).

Arguably intentional, since AdjBW is only meaningful in obesity, and the UI does display
"N/A" for AdjBW in that case. But the dosing-weight selector does not say so, and the value
used is not the one named. Document it or rename the option.

### P3 — The validation harness can silently drift from the app · **MEDIUM**

All three suites correctly extract the math from `index.html` rather than duplicating it — but
`const`/`let` are not readable out of a `vm` context, so each script **re-declares the model
constants by hand** (`Q_GOTI`, `OMEGA2_CL_GOTI`, `HUGHES_TVCL`, …). Change a constant in
`index.html` and every suite keeps testing the old value, green. Note that A1's threshold is a
`const`-adjacent literal of exactly this kind.

**Fix:** parse the constants out of the source text, or assert each mirrored constant against
a regex match on `index.html` so drift fails loudly.

### P4 — `CLAUDE.md` documents a UI that does not exist · **MEDIUM**

IDs `#b-ht` and `#model-select`. The app has **three module tabs plus four sub-modes**, uses
`.app-shell`/`.panel-left`, and the real ID is `b-height`. It also states 37 validation tests
(actual: 66) and ~6,400 lines / 279 KB (actual: 7,712 / 355 KB). Following it would send a
developer looking for elements that were never in this file. Rewrite, do not amend.

## Cleared — suspected defects that are not defects

**C1 — The two AUC methods agree.** `calcAUC` (analytic, `dose·(24/τ)/CL`) and
`calcAUC_trap` (linear trapezoid across the infusion + log-trapezoid across elimination) were
suspected of disagreeing. Swept over CrCl 20–120 and four regimens: **worst divergence
−0.31%** (2000 mg q24h, tinf 2 h, CrCl 120); typical −0.01% to −0.09%. The log-trapezoid limb
is algebraically exact for mono-exponential decay, and the linear chord across the infusion
gives up only a fraction of a percent. Clinically irrelevant. **No action.**

**C2 — The IBW 30 kg floor does not diverge in the adult range.** `calcIBW` (`:2926`) applies
`Math.max(…, 30)` while the inline copies at `:4787`, `:4807` and `:5112` do not. But Devine
only falls below 30 kg beneath ~135 cm (female), so across 137–183 cm the two forms are
**identical to machine precision**. The app does not support paediatrics. **No action** beyond
the general duplication concern.

**C3 — Goti's weight scaling on Vc is published, not invented.** I flagged `TVVc = 58.4·(wt/70)`
as an unsourced addition, because Goti's Table 2 lists only CrCL-on-CL, DIAL-on-CL and DIAL-on-Vc
as covariates. The Methods resolve it: *"parameters were normalized to a 70-kg individual before
other covariate relationships were examined"*, and the covariate-relationship block prints the
`/70` and `/120` centering explicitly. **Withdrawn.**
